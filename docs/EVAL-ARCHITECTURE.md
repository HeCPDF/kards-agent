## 1. Goal instruction（可直接作为 /goal 或交给 DS/subagent 的目标文本）

> **做出一个"盘外模拟器 + 评估器"：给定当前盘面快照和一步（或多步）操作，在盘外按 KARDS 原版规则把这步操作引发的连锁反应推演到稳态，输出"终态"；评估器只拿"终态 vs 起点"做比较，给出对胜负的价值差。**
>
> 1. **范围**：只收与对局胜负有关的状态变化（抽牌、贴膜/关键词增减、伤害治疗、移除/摧毁/移动/召唤/生成、指挥点/槽数/行动费、手牌牌库弃牌、压制/定住/免疫、转换、反制、随机结果等）；**表现类（音效、动画、特效、拍桌声、UI 提示、埋点）一律不要**。
> 2. **连锁到稳态**：一步操作可能触发连锁——抽牌触发抽到时效果，抽牌触发 autoplay，Trigger 触发其它牌的钩子，钩子再触发钩子……直到没有新事件为止（像化学体系加入一种物质后趋于稳态）。模拟器必须按**原版顺序**推演到终点，评估只比较终点与起点。
> 3. **覆盖**：胜负相关的**所有 native 函数**都要囊括（读侧求对，写侧在模拟里真实改状态）；**需要特殊处理的蓝图函数**（异步选择、随机、依赖行动上下文、递归触发顺序敏感等）单独处理；每个函数/钩子都有手写三段式规格（函数名 / 参数约定 / 实现）并能追溯到 IDA 结论。
> 4. **随机**：有活种子则按原版随机流确定推演（共用一条流，按原版顺序消费）；无种子则枚举分支并带概率。
> 5. **诚实**：取不到的效果记成"缺口"（gap），**不编造价值**；输出里必须带 `complete` 标志与缺口清单。
> 6. **架构**：**模拟（规则）与评估（价值）严格分层**；模拟按 KARDS 原版实现，不掺杂任何"对我们有利与否"的判断；代码可维护（单一规则来源、可追溯到规格、可回放校验）。
> 7. **验收**：(a) 195 个胜负相关 native 全部有实现与"换数据答案要变"的断言；(b) **预测 vs 实际留痕**：实机对局里每步记录模拟预测与游戏随后的真实结果（沿用现有 `meta` 留痕），差异逐条归因（回放测试台为可选工具，**不是前置**）；(c) 缺口清单只剩"未确认"类；(d) 单次决策模拟预算内（见 §3.7）；(e) 全部离线测试 + 实机至少 2 局无新问题。未达标则继续迭代，直到达标且旧问题关闭。

## 3. 架构标准

### 3.1 分层与依赖方向（只能向下依赖，禁止反向）
```
L4 策略/搜索（rule.py、搜索）      ── 枚举合法动作，调用 L2 得终态，调用 L3 打分，选最优
L3 评估（eval，纯函数）           ── score(起点, 终态, 上下文) → 价值差；不含任何游戏规则
L2 模拟器（sim，规则引擎）         ── simulate(状态, 动作序列, 随机源) → Outcome(终态, 事件轨迹, 缺口, complete, 概率分支)
L1 原语与规则库（natives / 钩子 / 分发顺序 / 随机流 / 蓝图运行器）
L0 状态与读取（kardsmem、kardsmem.board：内存只读 → 不可变快照）
```
- **L3 不得 import L2/L1 的规则实现**，只依赖 `State` 的数据结构；**L2 不得 import L3**（模拟不知道"好坏"）。
- L4 是唯一同时认识 L2 与 L3 的层，也是唯一与"我们要不要这么打"有关的层。
- L0 只读；L2 永不写游戏内存（符合红线）。

### 3.2 状态（State）
- 单一的、可复制（copy-on-write 或结构化拷贝）的状态对象：双方总部、各行单位（含攻防、关键词、被贴能力及来源、压制/定住、是否可行动）、手牌、牌库（已知顺序时保序）、弃牌、指挥点与槽数与上限、回合/行动方、**随机流状态（Seed）**、`enum_idx`（创建顺序）。
- 状态字段命名与游戏字段一一对应（便于追溯到 SDK），**不存"评估用的派生量"**（派生量放 L3）。
- 状态版本化：**不再绑 `KARDS_BUILD`/`build_tables.json`**（2026-10-03 取代）：版本由运行中游戏自报（`kardsmem/version.py`），RVA 运行时扫描（`ARCH-RELEASE-VCS.md`）。
- 新增字段（总纲 §4）：`autoplay_queue`（待打出队列，原版 `AddAutoPlayCards`）、`pending`（跨回合待生效项：预报选中的牌下回合 spawn、`kredit_next`…）、`prompt`（挂起时的提示）、`trace`。

### 3.3 模拟器（Sim）——按原版
- **事件驱动、跑到稳态**：动作 → 事件队列 → 按原版分发器顺序调用钩子（顺序 = 触发表元素序 = 卡牌创建顺序；自己的钩子先、others 后；反制先手等特例按 `ATTACK-HOOKS` §13）→ 钩子产生新事件入队 → 队列为空即稳态。设**步数/深度上限**防死循环（超限记缺口）。
- **写侧原语直接改 Sim 状态**（`ChangeKreditsBySide` 夹 [0, max]、`DrawCardsFromDeckBySide` 真抽牌并触发抽到时事件……），语义按 IDA 规格；**不再用"效果摘要字典 + 评估端解释"作为长期形态**（现状的 `eff` 字典是过渡产物，见 §5）。
- **蓝图运行**：外部 VM 直接跑蓝图字节码；需要特殊处理的蓝图函数（`IsActionProcess`、选择类、随机类、分发器、`CreateCard/Spawn*` 等）以"覆写表"统一登记，每条带原因与规格出处。
- **随机**：唯一入口 `RNG`（`kardsmem/rng.py` 的 `Stream`），整条链共用一个流；每次消费与原版步数一致（`RandomIntFromRangeWithStream` = d+2 步等）；无种子走枚举，输出带概率。
- **缺口协议**：遇到未实现/读不到 ⇒ 记入 `Outcome.gaps`（含函数名与原因），`complete=False`，**状态不做任何臆测更新**。
- **输出 `Outcome`**：`{state_end, trace(事件序列，可回放), gaps, complete, branches(概率分支, 可空), rng_used}`。`trace` 同时用于调试、回放校验和日志留痕。
- ★ **2026-10-03 修订**：`run` 的结果分两种——`Done`（稳态）/`Suspended(prompt)`（遇到需要**我们**做选择的点，策略逐候选 `resume`）。**随机由 `sim` 按种子直接算出确定结果，评估层不见随机**（没有 `Chance`、没有概率分支聚合）；读不到种子 ⇒ 记缺口并**换一个随机种子**照算法给结果（由 L5/适配层提供假种子，`sim` 永远照给定的种子算）。旧 `outcomes` 随机分支取期望与 `outcomes_mode=max` 仅为过渡。见 §3.8 与总纲 §4。

### 3.4 评估（Eval）
- 纯函数：`value(state)` 与 `delta(start, end, ctx)`；权重/参数集中在一个配置里，可单测、可调参。
- 只做价值判断：总部血量差、场面（单位价值/位置/可行动性）、手牌与牌库持有价值（已知真实牌则按真牌）、指挥点效率、威胁与致命线……**不得包含规则**（不得自己夹取、不得模拟触发）。
- 同回合计价规则放评估侧的上下文：重复牌 Δ≈0 记 0；贴膜后无后续攻击记 0；缺口项价值为 0（弯路 #38）。
- ★ 2026-10-03 取代：**评估层不处理概率分支**——随机已由 `sim` 按种子算成确定状态；读不到种子时记缺口并换随机种子，`sim` 照算法给确定结果，评估只对确定的状态打分。

### 3.5 可维护性标准
1. **单一规则来源**：每条规则只实现一处；实现旁注明规格出处（报告章节 + IDA 地址）。读侧 getter（原生）在 `natives` 库，写侧在 Sim 的状态变更 API，钩子分发在 `dispatch`，不得在评估/搜索里复制规则。
2. **文档—代码—测试三件套**：每个原生/钩子 = 一条手写三段式规格 + 一个实现 + 至少一条"换数据答案要变"的断言（弯路 #11）；覆盖率口径 = 有断言的比例，不是"能跑"。
3. **回放一致性比对（推荐，非前置）**：有条件时，把已录制对局（matchlog 动作流 + 前后快照）做成黄金样例，Sim 终态 vs 真实随后快照字段级比对，失败逐条归因。它是发现规格错/实现错/未接线的好工具，但**不阻塞实现**——每条规则已有单测断言与实机留痕作为验证。
4. **特殊处理注册表**：蓝图覆写、虚函数默认值、记录型 hook 都集中在表里，带 `reason`、`spec`、`status`，可枚举审计；不允许散落的 `if name == ...`。
5. **版本与构建隔离**：偏移、枚举、池（如三选一的预备名单）按构建/赛季版本化；对不上就报错并指明版本，不静默兜底（沿用 `build_check` 精神）。
6. **失败可见**：禁止宽泛 `except: pass` 吞错（弯路 #20）；错误进 `gaps` 或日志；`complete` 必须诚实。
7. **性能预算**：单次决策中，模拟总时长有硬预算（现状 `vm_budget_s` 3 s/回合 + 缓存）；按 (卡, 目标, 种子) 缓存；Sim 复制要廉价；超预算降级为"部分结果 + 缺口"，不阻塞回合。
8. **可观测**：每次决策记录 `trace` 摘要、缺口、预测 vs 实际（现有 `meta` 留痕），支持事后复盘。
9. **模块边界**（以 2026-10-03 现状为准）：`sim/{state,engine,adapter,chain,dispatch,effects}.py`（待建 `prompt.py`、`ops.py`）、`evaluation/{value,context}.py`（**不叫 `eval`**）、`policy/{search}.py`（待建 `paths/forced/plan`）；`kardsmem`、`kardsmem.board` 保持为 L0；`player/rule.py` 只做 L4 编排。公共接口仅 `simulate()`、`value()`、`delta()`，其余内部。
10. **变更纪律**：改规则 → 先改规格文档 → 再改实现 → 跑单测（有回放测试台则一并跑）→ 回执台账登记（`PLAN.md` §1.2）。

### 3.8 决策、提示与路径（2026-10-03 新增；总纲 §1/§3/§4 的评估侧落点）
- **一步操作的切分**：规划单位 = **决策** = 触发（我们的动词，或系统事件）+ 其后**全部提示的答案路径**，止于**稳态**（事件队列空 ∧ autoplay 队列已冲刷 ∧ 无悬挂提示）。移动、攻击同样（"攻击敌方总部时预报"= 一个决策）。
- **模拟遇到提示就挂起**：`Suspended(prompt, resume)`；`prompt.options` 来自游戏数据（抉择分支 / `GetChooseSpawnCards` 池洗牌取前 3 / `Forecast` 固定三张 / 手牌·目标合法性）；策略对每个候选 `resume`（copy-on-write）得到该路径终态。**预报 = 两层提示 = 9 条路径**，抉择牌 = k 条，三选一池类 = 3 条。
- **每个决策最多 24 条叶路径 + 剪枝**（在策略层做：先给各前缀的挂起态打粗分再展开；同牌路径进束前先剪；束宽不动）。
- **强制决策**：提示由系统事件引发（回合开始钩子如 PBY CATALINA、autoplay 冲刷）——搜索里无法预定，弹出时 `policy.forced.answer` 当场枚举；模拟里抽牌/塞牌遇到 autoplay 牌 ⇒ **入 `autoplay_queue`**，在动作边界冲刷（免费 `PlayCardFromHand`）。
- **延迟项**：跨对手回合的后果进 `State.pending`，由评估估值（默认口径：下回合开始、盘面不变；meta 标明），模拟**不跨**对手回合。
- **评估侧新增**：`value_pending`（延迟项）。没有 `aggregate`：评估不见随机，`Suspended` 由策略取最好。

### 3.6 与红线的关系
Sim 只读游戏内存、不写；注入侧读查询（`Can*`）仍是判据，**不用 Sim 否决动作**（"判据负责挑，游戏负责判"）。Sim 的输出只用于排序与选择。

### 3.7 性能与降级
- 决策预算：每步 ≤ 约 1 s（含搜索），每回合 ≤ 35 s 总预算内；超限时 Sim 返回 `complete=False` 的部分结果。
- 深度策略：默认单步动作 + 其连锁到稳态；多步计划（组合）由 L4 控制深度，Sim 不负责搜索。

## 7. 钩子顺序与互斥：已查与未查（供实现者与后续调研）
**已查（`CARD-PLAY-HOOKS-1.60.md` §176–202、`ATTACK-HOOKS-1.60.md` §13）：**
- 同一动作内：**反制先手**，按 `GetActiveGotchasOrdered` 排序（key = `gotchaActivated` 即"挂上的先后"升序；`card_event_ultra` 与 `card_event_interception` 有特殊键），然后才是自己的钩子，再是 others（触发表元素序 = 卡牌创建顺序）。
- **互斥/中止**：`SetStopFurtherActions` — 某张反制触发后可置位，**中止该动作剩余的所有钩子**（出牌 `CardPlayedFromHand`、上线 `ExecuteOnMoveToFrontlineCardEffects`、`ExecuteOnCardDealDamageEffects` 等）；`stopAttack` / `AttackedAndStopped` 对攻击的吞并规则见 ATTACK-HOOKS §2。
- 反制能否触发：`ShouldGotchaTrigger`（0x144B0DDD0）——须在手牌、已挂上、属于非当前行动方；`sideeffect.blockgotcha` 或任一牌带 `stop_gotcha` 则不触发；触发后 `gotchaActivated=0`、入弃牌堆、重排手牌，并发 0x15 `OnCounterMeasureTriggered`。
**未查 / 未实现（需要专项调研）：**
1. `GetStopFurtherActions` 的叫停语义在**每一条链**里的精确位置（哪几个钩子之后检查、之前已执行的是否回滚）——`triggers.py` 标为"未实现"。
2. **多张反制同时满足条件时**的相互作用：第一张触发后（摧毁/取消/改目标）第二张的条件是否被重新评估、是否因 `instigator.enterPlayOnTurn=0` 等被动失效。
3. 非反制钩子里"结果与顺序严格相关"的**清单**（同一触发点上两张牌互相影响：先加攻再翻倍、先摧毁再给增益、先压制再触发……）——目前只有"创建顺序"这一条总规则，没有按卡逐个验证。
4. 触发表在原生侧是否"只加不删"、新创建的牌何时进入表（顺序随创建变化）。
5. 敌方反制对**我方动作**的评估口径（方向语义），`rule` 目前未算。
**要求**：Sim 对顺序与互斥必须按上面"已查"部分如实实现；"未查"部分在实现里一律记缺口（`complete=False`），**不得猜顺序**。
